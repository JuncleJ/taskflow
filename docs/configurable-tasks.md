# Настраиваемые DEMO и CPU_TASK

Реализация `prompts/004-configurable-tasks.md`. Архитектура HTTP → TaskService → TaskExecutor → TaskHandler
сохранена. Отмена, удаление, проверка владельца и политика восстановления после перезапуска продолжают действовать.

## Запросы и параметры

```json
{
  "type": "DEMO",
  "durationSeconds": 20
}
```

`durationSeconds` — целое JSON-число от 1 до 300 включительно. Если поле отсутствует, используется 5 секунд.
Явный null, строки, дробные числа, boolean, выход за диапазон и неизвестные поля возвращают HTTP 400 до создания
строки задачи. Поддерживаются только DEMO и CPU_TASK. Создание REPORT возвращает HTTP 400.

```json
{
  "type": "CPU_TASK",
  "limit": 1000000
}
```

`limit` обязателен: целое JSON-число от 2 до 10 000 000 включительно. Подсчитываются простые числа на включительном
диапазоне [2, limit]. Граница 10 миллионов ограничивает объём перебора для учебного приложения. Алгоритм проверяет
делители до квадратного корня и использует O (1) дополнительной памяти, без большого решета или массива.
Это реальная CPU-нагрузка; длительность зависит от машины и нагрузки, лимит не является гарантией времени выполнения.

Нормализацию выполняет сам TaskHandler через `parameters(...)`; для добавления другого типа движок не меняется.
Снимок задачи содержит объект `parameters`, например `{"durationSeconds":20}` или `{"limit":1000000}`.
Он сохраняется в PostgreSQL JSONB и передаётся в HTTP/SSE. В Task параметры защищены копированием от внешнего изменения.
Идемпотентный `db/003-task-parameters.sql` добавляет колонку существующим базам. У старых задач параметры остаются `{}`;
для старого DEMO это означает прежние 5 секунд. Исторические строки не переписываются при каждом старте.

## Выполнение DEMO

`DemoTaskHandler` использует монотонное время System.nanoTime и неблокирующие таймеры Vert.x.
Проверка происходит не реже ближайшего тика до 250 мс при свободном Event Loop. Запись прогресса выполняется только
при изменении целого процента, всего не более 100 обновлений. Задержки PostgreSQL не прибавляются к каждому шагу
фиксированного расписания: следующий процент определяется по реально прошедшему времени.
Если БД или процесс задержались, промежуточные проценты могут быть пропущены, а завершение наступит позднее
заданной длительности. Сигнал отмены проверяется на каждом тике и перед записью прогресса.

## Выполнение CPU_TASK и потоки

`CpuTaskHandler` владеет отдельным ThreadPoolExecutor: фиксированное число потоков `taskflow-cpu-*`,
ArrayBlockingQueue и AbortPolicy. CallerRunsPolicy не используется: при насыщении пула вычисления никогда
не переходят в вызывающий Event Loop. Принятая движком задача при отказе CPU-пула завершается FAILED;
в журнале остаётся тип RejectedExecutionException.

CPU-worker проверяет CancellationToken на каждой итерации перебора. Прогресс публикуется с шагом 5%,
не более 20 обновлений на задачу. SQL на каждой итерации отсутствует. Callback прогресса передаётся
через исходный Context.runOnContext, поэтому коллекции TaskExecutor, PostgreSQL-операции и SSE
обрабатываются в том же контексте, что и до добавления CPU-задач.

Worker ожидает подтверждения записи своего checkpoint; ожидание выполняется только в CPU-потоке.
На задачу приходится не более одного ожидающего callback. Проверка отмены во время ожидания — каждые 100 мс,
общий таймаут подтверждения — 30 секунд. При отказе/таймауте записи вычисление прекращается.
TaskExecutor по-прежнему ждёт уже начатые SQL-записи перед сохранением терминального состояния.

Отмена ещё не начатой работы удаляет её из очереди CPU-пула. Для уже работающего worker отмена кооперативная:
он прекращает перебор, завершается Future обработчика, затем сохраняется CANCELLED и освобождается слот движка.
Само HTTP-ожидание отмены не блокирует Event Loop. При естественном завершении лог содержит primeCount (например, для
limit=1000000 — 78498); отдельное поле результата в БД/API не добавлялось.

## Ограничения нагрузки и остановка

| Переменная          | По умолчанию | Допустимые значения                                          |
|---------------------|--------------|--------------------------------------------------------------|
| CPU_WORKERS         | 2            | 1–32                                                         |
| CPU_QUEUE_CAPACITY  | 16           | 1–256                                                        |
| TASK_QUEUE_CAPACITY | 100          | 1–10000                                                      |
| TASK_PARALLELISM    | 3            | положительное целое; существующий общий лимит активных задач |

Значения передаются через окружение JVM или `.env` Docker Compose. Размеры CPU-пула и очереди проверяются при старте.
Общая очередь движка теперь также ограничена. TaskService резервирует место до INSERT, учитывая создания,
ещё ожидающие PostgreSQL; при насыщении возвращается 429 без создания задачи. Ошибка INSERT освобождает резерв.
Фактическое число одновременно считающих CPU_TASK не превосходит min (CPU_WORKERS, TASK_PARALLELISM).
Превышение вместимости CPU-пула возможно при настройке большого TASK_PARALLELISM и маленькой очереди CPU;
такие уже принятые задачи переходят в FAILED, не накапливаются бесконечно.

При остановке приложение прекращает запуск задач, запрашивает отмену активных выполнений и закрывает CPU-пул.
Ожидание завершения пула вынесено в executeBlocking только для процедуры shutdown, не для вычислений.
После 5 секунд предусмотрен shutdownNow с завершением Future снятых с очереди работ, затем ещё до 5 секунд ожидания.
PostgreSQL pool закрывается и в случае ошибки остановки CPU-пула. При аварийном завершении процесса
незавершённые записи, как и раньше, становятся FAILED на следующем запуске; параметры сохраняются.

## Интерфейс и проверки

В интерфейсе добавлены числовые поля durationSeconds и limit и кнопка CPU_TASK. Параметры видны на карточках.
Существующие прогресс/SSE, «Отменить» и «Удалить» работают и для CPU_TASK.

- DemoTaskHandlerTest: реальные 5 секунд по умолчанию, границы 1/300, неверные значения и отмена длинного DEMO.
- CpuTaskHandlerTest: известные количества простых чисел, ограничение числа обновлений, реальные CPU-потоки,
  параллельная работа, пределы пула/очереди, отмена активной/ожидающей работы, ошибки прогресса и остановка потоков.
- ConfigurableTaskServiceTest: нормализация/защита параметров и резервирование общей очереди при асинхронном INSERT.
- PostgresTest: JSONB, сохранение параметров при обновлении и восстановлении.
- SseIntegrationTest: настоящие DEMO/CPU_TASK, HTTP-валидация, сохранение параметров, завершение/отмена через SSE
  и доступность HTTP при двух активных CPU_TASK. Сценарии гонок SSE используют отдельный CONTROLLED-обработчик.

В тестах параллелизма/отмены подтверждение checkpoint можно удержать тестовым Future, чтобы проверить точный
момент отмены, не полагаясь на скорость CPU. Это не заменяет алгоритм или PostgreSQL и не является нагрузочным
бенчмарком.
Интеграционные тесты требуют TEST_DB_* и отдельного PostgreSQL; без TEST_DB_PORT они явно пропускаются.

Результат проверки: `gradlew.bat clean build test --rerun-tasks` — BUILD SUCCESSFUL,
все 63 теста прошли без ошибок и пропусков с отдельным PostgreSQL 16.3. Реальный DEMO по умолчанию
проверен на 5 секундах, настроенный — на 1 секунде; CPU_TASK проверен на известных результатах до limit=1000000.
Тест с двумя активными CPU_TASK выполнил HTTP-запрос в пределах таймаута 2 секунды.
`node --check src/main/resources/webroot/app.js` — успешно. Визуальная проверка браузером и Docker-запуск не
выполнялись.

## Оставшиеся ограничения

- Приложение рассчитано на один экземпляр; общая очередь и сигналы отмены локальны процессу.
- Число worker-потоков ограничено, но CPU-квоты ОС, справедливость между пользователями и автоматическое
  определение свободных ядер не реализованы. Настройки нужно выбирать под ресурсы машины.
- Медленная БД занимает CPU-worker ожиданием checkpoint и снижает пропускную способность, хотя Event Loop не
  блокируется.
- Результат primeCount записывается в лог, но не хранится как отдельный результат задачи.
- Автоматический повтор при отказе пула/БД отсутствует; действуют существующие статусы FAILED и политика перезапуска.
- Визуальная проверка браузером, Docker-запуск и длительное нагрузочное тестирование не заменяются интеграционными
  тестами.
