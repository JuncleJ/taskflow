# TaskFlow

Приложение для асинхронного выполнения фоновых задач с сохранением прогресса в PostgreSQL и обновлением интерфейса через
Server-Sent Events.

Стек: Java 21 (Eclipse Temurin), Vert.x 5.2.2, Reactive PostgreSQL Client, PostgreSQL 17 в Compose, Gradle 8.14.3 Kotlin
DSL, JUnit 5. Интерфейс — HTML/CSS/JavaScript без фреймворков. SQL дополнительно проверен на PostgreSQL 16.

## Запуск через Docker Compose

Нужны Docker Engine и Docker Compose v2.

1. Скопируйте `.env.example` в `.env`.
2. Укажите собственный непустой `DB_PASSWORD` в `.env`.
3. Выполните `docker compose up --build`.
4. Откройте <http://localhost:8080>, зарегистрируйтесь и запустите DEMO или REPORT.

База хранится в Docker volume `postgres-data`. `docker compose down` сохраняет данные. Инициализация таблиц происходит
автоматически при запуске приложения; HTTP-сервер начинает принимать запросы только после подключения к БД и
восстановления задач.

## Локальный запуск

Нужны JDK 21 и доступный PostgreSQL. Gradle Wrapper включён в проект и загружает Gradle при первом запуске. `.env`
читает Docker Compose; при локальном запуске переменные необходимо экспортировать самостоятельно.

Пример PowerShell:

```powershell
$env:JAVA_HOME = 'C:\путь\к\temurin-21'
$env:DB_HOST = 'localhost'
$env:DB_PORT = '5432'
$env:DB_NAME = 'taskflow'
$env:DB_USER = 'taskflow'
$env:DB_PASSWORD = Read-Host 'Пароль PostgreSQL'
.\gradlew.bat run
```

Базу и роль создайте заранее либо запустите только PostgreSQL через `docker compose up -d db`. В Linux/macOS используйте
`./gradlew run` (если требуется, сначала `chmod +x gradlew`).

## Архитектура

```text
HTTP / статические файлы
  Routes → AuthService → PgAuthStore
         → TaskService → PgTaskStore → PostgreSQL
                      → TaskExecutor → TaskHandlerRegistry → TaskHandler
                                      ↓ сохранённые снимки
                                SseNotifications → браузер
```

`Main.Application` связывает компоненты в одном Vert.x context. HTTP-слой проверяет формат запросов, токен и владельца,
преобразует ошибки в JSON. Бизнес-логика создания задач расположена в `TaskService`; хранилища используют
параметризованные запросы Reactive PostgreSQL Client. Все выборки отдельных задач и списка ограничены владельцем, чужой
UUID возвращает 404, в том числе для SSE.

Пароли хешируются PBKDF2-HMAC-SHA256 с 600 000 итераций и случайной 16-байтной солью. CPU-затратное хеширование
выполняется через `executeBlocking(..., false)` в worker pool, не в Event Loop. Для отсутствующего пользователя
выполняется проверка фиктивного хеша. Токен содержит 32 случайных байта, в БД сохраняется только SHA-256 токена и срок
действия 24 часа. В браузере токен хранится в `sessionStorage`; SSE использует потоковый `fetch` с `Authorization`, без
токена в URL.

### Выполнение задач

После записи `PENDING` API возвращает 202 и снимок с UUID, не ожидая завершения. Исполнитель берёт задачи из очереди,
запускает не более `TASK_PARALLELISM` обработчиков. Перед каждым событием сохраняет `RUNNING`, прогресс, затем
`COMPLETED` или `FAILED`, временные метки и описание ошибки. Сбой одного обработчика освобождает слот для следующей
задачи. Прогресс должен возрастать и оставаться в диапазоне 0–100.

DEMO делает 10 шагов с паузой 500 мс, REPORT — 4 этапа по 1 секунде. Ожидание реализовано одноразовыми таймерами,
операции БД асинхронны. Чтобы добавить тип, реализуйте `TaskHandler` и зарегистрируйте его в `TaskHandlerRegistry` при
сборке приложения; движок менять не требуется. Обработчик должен возвращать `Future`, последовательно ожидать результаты
callback прогресса и не блокировать Event Loop. Реальные блокирующие операции следует выносить в worker pool.

SSE отправляет текущее состояние и события `progress`, `completed`, `failed`. После терминального события соединение
закрывается. Heartbeat раз в 15 секунд, удаление подписчиков при отключении, отключение медленных клиентов при
заполнении выходной очереди. Повторное чтение после подписки закрывает окно между первой выборкой и подключением;
устаревшие снимки не уменьшают прогресс. Клиент переподключается через 2 секунды после разрыва и получает актуальный
снимок.

### Перезапуск

При каждом запуске `Database.initialize` переводит сохранённые `PENDING` и `RUNNING` в `FAILED` с ошибкой «Приложение
перезапущено» и временем завершения. Сохранённый прогресс остаётся доступным. `COMPLETED` и уже завершённые `FAILED` не
меняются. Автоматического повтора нет: пользователь создаёт новую задачу. Просроченные сессии удаляются при запуске.

## REST API

Все тела — JSON. Логин: 3–64 латинских букв, цифр или `_`; пароль: 8–128 символов. Тип задачи — `DEMO` или `REPORT`.

| Метод | Путь                    | Ответ                                   |
|-------|-------------------------|-----------------------------------------|
| POST  | `/api/auth/register`    | 201, `{token, expiresIn}`               |
| POST  | `/api/auth/login`       | 200, `{token, expiresIn}`               |
| POST  | `/api/tasks`            | 202, объект задачи, заголовок Location  |
| GET   | `/api/tasks`            | 200, до 200 последних собственных задач |
| GET   | `/api/tasks/:id`        | 200, объект задачи                      |
| GET   | `/api/tasks/:id/events` | 200, `text/event-stream`                |

Ошибки: 400 — некорректный запрос, 401 — недействительный токен/пароль, 404 — задача недоступна, 409 — логин занят,
500 — внутренняя ошибка. Формат: `{"error":"описание"}`.

Примеры для bash (в PowerShell используйте `curl.exe` и подходящее экранирование JSON):

```bash
curl -X POST http://localhost:8080/api/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"login":"alice","password":"replace-this-password"}'

curl -X POST http://localhost:8080/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"login":"alice","password":"replace-this-password"}'

# Подставьте полученный токен и UUID задачи.
export TOKEN='полученный-токен'
curl -X POST http://localhost:8080/api/tasks \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"type":"DEMO"}'
curl http://localhost:8080/api/tasks -H "Authorization: Bearer $TOKEN"
curl http://localhost:8080/api/tasks/UUID -H "Authorization: Bearer $TOKEN"
curl -N http://localhost:8080/api/tasks/UUID/events -H "Authorization: Bearer $TOKEN"
```

## Сборка и тесты

```powershell
.\gradlew.bat clean build
.\gradlew.bat test --rerun-tasks
```

В Linux/macOS — `./gradlew`. Дистрибутивы появляются в `build/distributions`, HTML-отчёт тестов —
`build/reports/tests/test/index.html`.

Тесты проверяют соль и пароли, токены, жизненный цикл, ошибки и валидацию прогресса, ограничение параллелизма и
продолжение очереди, регистрацию/вход, REST, изоляцию пользователей и SSE. Обычный запуск использует тестовые хранилища
в памяти. Два интеграционных теста SQL включаются переменной `TEST_DB_PORT`:

```powershell
$env:TEST_DB_HOST = 'localhost'
$env:TEST_DB_PORT = '5432'
$env:TEST_DB_NAME = 'taskflow'
$env:TEST_DB_USER = 'taskflow'
$env:TEST_DB_PASSWORD = $env:DB_PASSWORD
.\gradlew.bat test --rerun-tasks
```

Интеграционные тесты создают случайную отдельную схему и удаляют её после теста; роль должна иметь право `CREATE` в
выбранной БД. Без `TEST_DB_PORT` эти проверки явно пропускаются. Проверяются реальные SQL-переходы, изоляция,
восстановление после перезапуска, уникальность логина и истечение сессий.

### Результаты первичной проверки

Проверено на Windows с Eclipse Temurin 21.0.13 и отдельным временным PostgreSQL 16.3:

- `gradlew.bat clean build test --rerun-tasks` — успешная чистая сборка с интеграционными тестами.
- После исправления обнаруженной ошибки освобождения SSE-подписки: `gradlew.bat build test installDist` — успешно, все
  11 тестов прошли, пропусков нет.
- Запуск собранного дистрибутива и HTTP-сценарии DEMO/REPORT с реальной БД: регистрация, 202 при создании, событие SSE
  `completed`, сохранённый статус `COMPLETED` и прогресс 100%.
- Регрессионный тест проверяет отсутствие исключений heartbeat после завершения SSE.
- Docker-сборка и запуск Compose не проверялись: Docker отсутствует в окружении. Визуальная проверка интерфейса
  браузером не выполнялась.

## Ограничения первой версии

- Поддерживается один экземпляр приложения: очередь и SSE-подписчики находятся в памяти. Несколько экземпляров потребуют
  общей очереди, координации восстановления и доставки событий.
- Очередь ожидающих задач не ограничена; нет отмены, повторов, таймаутов обработчиков, квот и rate limiting. Перед
  публичным запуском нужны ограничения нагрузки и HTTPS через reverse proxy.
- При недоступности БД исполнитель записывает ошибку сохранения через SLF4J на ERROR; оставшиеся незавершённые задачи
  будут помечены FAILED при следующем запуске. Надёжной доставки и автоматического восстановления соединений задач нет.
- SSE передаёт актуальное состояние, без журнала и воспроизведения каждого промежуточного события. При переподключении
  промежуточные шаги могут быть пропущены.
- DEMO и REPORT имитируют работу, файлового результата отчёта нет.
- Выход в интерфейсе удаляет локальный токен, серверная сессия действует до истечения 24 часов. Нет сброса пароля и
  отзыва сессий.
- Схема создаётся идемпотентным SQL, полноценные версионированные миграции пока отсутствуют.
- Docker Compose требует отдельной проверки в окружении с Docker. Автоматизированного браузерного теста интерфейса нет.

не изменялись.
